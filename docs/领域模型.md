# 成长与岗位衔接服务 · 领域模型

老字号大师工作室与技能学校共用一套事实：课程目标、工艺能力、现场作品、导师观察**各自保留来源**；
能力是否成立由**学校与工作室按当时规则共同确认**；一切补充与撤回都以新事件表达，**历史不被抹掉**。

## 1. 核心原则

| 原则 | 落地方式 |
| --- | --- |
| 证据各带来源、互不相认 | 每条证据带 `source_type`（`school_grade` / `mentor_observation` / `shop_work`）与来源机构；规则要求至少两类不同来源且达到权重，单一来源满分也不成立 |
| 认定须双机构、按当时规则 | `ConclusionDerived` 记录 `rule_version`；`ConfirmationRecorded` 必须同时存在 school 与 studio 各一条 |
| 只追加、不改写历史 | 账本只追加事件；撤回=新增 withdrawn/invalidated/revoked/superseded 标记，原记录永久保留 |
| 隐私最小化外发 | 跨机构只发"能力已认定"摘要；联系方式与任何评价正文不进入摘要；授权撤回后拒绝再次出具 |
| 排班随条件自动重算 | 证据撤回、确认撤销、规则升级、导师停带、工坊暂停都会让受影响安排失效；仍在生产且有人选时立即重排 |
| 重复提交结果一致 | 每个命令带 `command_id`；重放同一命令返回首次产生的同一批事件 |

## 2. 模块

- `src/ledger.js` — 只追加事件账本（`EventLog`），维护命令幂等表。
- `src/catalog.js` — 能力目录与规则版本（`rule-v1` / `rule-v2`），纯函数 `evaluate` / `gatesOpen`。
- `src/projection.js` — 从事件流顺序折叠出当前状态（`fold`）。
- `src/service.js` — `GrowthService`：命令、资格判定、自动失效重算、读模型。
- `src/ingest.js` — 把既有工作室与课程记录（`fixtures/seed.json`）以命令方式纳入。
- `fixtures/seed.json` — 领域样例：老奉泰大师工作室、东城技能培训学校、三名学徒、协作作品、公开/未公开评价、v1→v2 规则升级、跨工作室授权、生产班次。

## 3. 规则版本

- `rule-v1`：能力项须权重 ≥2 且至少两类不同来源；无硬门槛。
- `rule-v2`（2026-09-01 起）：在 v1 基础上新增**硬门槛 `食品安全合规`**。硬门槛不参与多源加权，有任一有效凭证即通过；无凭证者即使工艺能力齐全也**不得进入生产班**。

规则只能新增版本，不能改旧版本。结论永远携带形成时的版本；历史决定永远按当时规则解释，排班资格则按当前版本复核（含门槛）。

## 4. 事件清单

注册与组织：`OrganizationRegistered` `StudioRegistered` `MentorAppointed`
`MentorshipEnded` `ProductionPaused` `ProductionResumed` `PersonEnrolled`
`CourseDefined` `PositionDefined` `ShiftOpened` `RulePublished`

证据与认定：`EvidenceSubmitted` `EvidenceWithdrawn` `ConclusionDerived`
`ConfirmationRecorded` `ConfirmationRevoked`

授权与外发：`ConsentGranted` `ConsentWithdrawn` `SummaryIssued`

排班：`AssignmentCreated` `AssignmentInvalidated`

### 结论链（不可变）

同一人同一能力每次证据变动都产生一条新 `ConclusionDerived`：

```
结论A(active) ──补充/撤回证据──▶ 结论B(active)，结论A → status=superseded, superseded_by=B
```

确认只挂在**当时现行**结论上；旧结论被取代后需对新结论重新确认。

## 5. 不变量

1. 协作作品（同一 `work_id` 多人提交，或本人登记了协作者）必须写 `contribution`，否则拒绝提交。
2. 同一机构对同一结论只能确认一次；确认主体必须是 school 或 studio。
3. 进入班次的人须同时满足：岗位技能均有"满足 + 双确认"结论、硬门槛有有效凭证、与既有在班安排时间不重叠、工坊在产、指导导师未停带。
4. 工坊暂停期间不产生任何新安排；复工后为失去现行安排的开放班次重排。
5. 授权摘要对象不含 `contact`，不含证据/评价正文，只含能力名、规则版本、确认者与确认时间。
6. 任意时刻重放整条事件流得到唯一终态——这是跨机构确认、撤回、规则升级"结果彼此一致"的最终保障。

## 6. 读模型

- `onboarding(assignmentId)`：门店一次查看上岗决定，得到
  课程 → 阶段/成绩 → 现场作品与本人贡献 → 结论与规则版本 → 学校/工作室确认者 → 硬门槛凭证 → **仍缺训练** 的完整链路；失效决定同时返回失效原因与替代安排。
- `shiftCandidates(shiftId)`：逐人给出是否合格、能力缺口与时间冲突。
- `portableView(consentId)`：授权范围内可携带的能力摘要。

## 7. 场景对照

| 题目场景 | 对应行为 / 测试 |
| --- | --- |
| 二十四褶已会却被要求重修 | 多源结论保留全部来源，只有双确认才认定（"单一来源不能认定"测试） |
| 未过食品安全反进生产班 | v2 硬门槛阻断（"阿炳不能进入生产班"测试） |
| 补充或撤回证据 | 只新增结论，旧结论 superseded、证据 withdrawn（对应测试） |
| 协作作品写贡献 | 无贡献拒绝、有贡献落库（协作作品测试） |
| 转工作室携带摘要 | 授权摘要最小化，撤回即失效（授权/撤回测试） |
| 能力满足 + 时间不冲突才排班 | 资格判定与时间冲突测试 |
| 导师停带 / 工坊暂停 | 自动失效、复工重算（对应测试） |
| 门店追溯 | `onboarding` 测试 |
| 跨机构确认、规则升级、重复提交、撤回授权一致 | 规则升级、幂等、重放一致性测试 |
